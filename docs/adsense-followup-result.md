# 광고 준비 후속 검증과 배포 기록

기준일: 2026-11-02. 사용자가 남은 작업의 진행과 배포를 요청했다. 광고 활성화와 main 병합은 배포와 구분한다. 광고는 계속 비활성화한다.

## 완료한 추가 작업

- 클로드 보안 PR #111의 head `6116eba68bb96cab5d5c872d9949a362ef15fc36`을 기준 main `32a422e`와 비교해 두 관점으로 검토하고 이 작업 브랜치에 통합했다.
- 새 가입 비밀번호는 8자 이상으로 제한한다. 기존 4~7자 비밀번호 계정의 로그인과 운영자 비밀번호 변경 동작은 유지한다.
- Vercel·Cloudflare 정적 파일·Worker 응답의 CSP를 동일한 생성기로 관리한다. 현재는 **보고 모드**이며 실제 차단이나 원격 위반 수집을 켰다고 주장하지 않는다.
- 홈페이지 수정에 맞춰 CSP 해시를 다시 만들었다. Windows CRLF와 HTML 파서의 LF 정규화 차이로 인라인 해시가 어긋나는 문제를 재현하는 테스트가 실패하는 것을 확인한 뒤 수정했다. 생성 헤더 3개는 Git에서도 LF를 유지한다.
- CSP 브라우저 검사의 고정 대기 시간을 실제 화면/위반 이벤트 조건으로 바꿨다. 외부 스크립트 검증은 예약된 예시 도메인을 로컬에서 가로채므로 실제 외부 코드를 내려받지 않는다. 새 이용규칙·출처 페이지도 검사한다.
- 실제 Chromium 서비스 워커를 사용해 구버전 캐시를 가진 방문자의 업데이트를 검사했다. 초기 설치 이벤트와 새 워커의 활성화가 다르므로 교체 워커의 `activated` 상태를 직접 기다린다. 테스트 수정 전 실패 로그도 보존했다.
- 구 캐시 제거, 현행 지형 SHA-256 일치, 오래된 manifest 캐시 우회, 오프라인 이미지 읽기, 친절한 오프라인 화면과 다시 시도 버튼의 온라인 복귀를 확인했다.

## Standards

독립 검토에서 확인된 항목 1개: `browser-csp.js`의 고정 500ms 대기 뒤 비동기 위반 이벤트를 단정하는 검사는 결정적 대기 규칙에 맞지 않는다. 실제 이벤트 조건과 제한 시간으로 수정했다. 문서화된 규칙의 다른 위반이나 중대한 코드 냄새는 발견되지 않았다. 이 리뷰는 검토자 자신의 테스트 실행 결과가 아니다.

## Spec

PR 자체에서 확인된 누락·범위 이탈·중대한 구현 문제는 0개였다. 통합 시 우리 홈페이지 스크립트의 변경으로 CSP 해시를 다시 생성해야 한다는 요구가 확인되어 반영했다. 보고 모드의 미차단·원격 수집 부재는 원래 명시된 제한이다.

두 관점의 요약: Standards 1개(비동기 검사 신뢰성, 수정), Spec 0개(PR 자체), 별도 통합 요구 1개(해시 재생성, 반영).

## 계정 및 배포 상태

Chrome의 기본 Google 계정에서는 ‘애드센스 계정 없음’이라는 화면을 확인했다. 다른 계정에 가입 여부가 있는지는 계정 선택 답변을 기다린다. 가입·약관·신원·지급 설정은 수행하지 않았다. 게시자 ID를 만들거나 추정하지 않았다.

Vercel 연결 도구에서 대상 프로젝트가 보이지 않고 CLI 인증 오류가 있어, 이미 로그인된 Chrome의 기존 `sgh1101s-projects/13fps` 프로젝트를 확인했다. 이 프로젝트는 `Sgh1101/DFDF`와 연결되어 있고 운영 커밋은 배포 전 `32a422e`였다. 기존 프로젝트와 도메인 `13fps.xyz`를 사용하며 새 프로젝트나 유료 기능을 만들지 않는다.

배포 절차: 테스트한 정확한 커밋을 작업 브랜치에 push → 해당 커밋의 Vercel 배포를 생성 → Ready 및 커밋 확인 → Production으로 승격 → 실제 `/api/release`, 공개 문서·보안 헤더·핵심 자산·브라우저 화면을 확인한다. main은 별도로 합치지 않는다. 차후 main의 자동 배포가 이 배포를 교체할 수 있으므로 추후 통합 시 이 브랜치의 변경을 포함해야 한다.

현재 문서 작성 시점은 배포 직전이다. 실제 배포 결과와 식별자는 로컬 최종 배포 증거 파일에 추가한다. Google 계정/승인, 대상 이용자·인증 CMP, 자산의 미확인 표현 권리는 실제 광고 도입 전까지 남는다.

## 작업 중 내린 판단

- 사용자의 배포 요청을 기존 Vercel 서비스 배포 승인으로 적용했다. 별도 main 병합 승인으로 확대하지 않는다.
- 클로드 보안 변경은 이 브랜치에 통합하되 보고 모드를 유지한다. 새로운 보안 헤더가 실제 차단을 제공한다고 과장하지 않는다.
- 없는 실기기나 비실행 Docker 때문에 독립적인 코드·브라우저 검증을 중단하지 않았다. 그 결과를 실제 기기·Redis 검사로 표시하지 않는다.
- 연결 도구의 404 및 CLI 인증 문제로 새로운 자격 증명을 추출하지 않고 기존 브라우저 세션의 정상 배포 UI를 사용한다. 권한 확대·계정 변경·인증 정보 공개는 하지 않는다.
