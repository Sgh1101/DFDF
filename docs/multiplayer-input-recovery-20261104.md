# 참가자 위치 되돌림 조사와 입력 복구

## 신고와 확인된 범위

방장은 PC, 총 2~4명이며 방장 외 참가자들이 대전 중 안내 문구 없이 멈추거나 위치가 계속 되돌아간다는 신고다. 게스트 계정의 로그인 문제를 뜻하지 않는다.

확인된 결함은 순서가 바뀐 이동 입력의 유실이다. PeerJS 상태 채널은 순서를 보장하지 않는데, 방장은 더 큰 입력 번호를 받은 뒤 도착한 이전 입력을 버렸다. 이전 패킷의 이동 시간은 새 패킷에 포함되지 않아 참가자의 예측보다 적게 이동하고, 이후 스냅샷이 그 차이를 되돌렸다.

수정 전 실제 입력 생성·수신 함수를 사용하는 단위 재현에서, 6개 입력을 `2,1,4,3,6,5` 순서로 전달하면 참가자의 예측은 1.002m, 방장의 인정 거리는 0.501m였다. 두 패킷씩 빠진 경우에는 0.334m만 인정했다. 이 경로는 수정 후 동일 거리를 인정한다. 신고된 장시간 멈춤의 원인까지 확정한 것은 아니다.

## 변경

- 참가자의 새 입력에 직전 3개 이동 명령을 함께 보낸다. 각 명령의 방향, 시선, 버튼, 이동 시간과 세부 프레임 시간을 보존한다.
- 방장은 아직 받지 않은 유효 명령만 입력 번호 순서대로 복구한다. 이미 수신한 명령은 시간 형식이 전환되더라도 다시 실행하지 않는다.
- 기존 이동 시간 제한과 입력 대기열 상한을 유지한다. 복구 명령도 동일한 입력·시간 검사를 거친다.
- 연결, 조종하는 몸체, 라운드가 바뀌거나 방을 떠나면 복구 이력과 미완성 입력 시간을 초기화한다.
- 복구 이력을 모르는 이전 클라이언트·방장과 기본 패킷 형식을 유지한다. 복구 효과를 얻으려면 방장과 참가자가 모두 수정 버전을 사용해야 한다.

입력 패킷은 최대 3개 명령만큼 커진다. 긴 통신 단절이나 복구 범위를 넘는 연속 유실, 렌더링 성능 문제까지 해결하는 변경은 아니다. 모델·음원·챔피언스 효과와 호스팅 설정은 변경하지 않는다.

라운드·몸체 변경 검사는 참가자의 로컬 이력 초기화를 확인한다. 이미 전송 중인 이전 라운드·몸체의 패킷을 별도 세대 번호로 판별하는 변경은 포함하지 않는다.

## 검증

실행 로그는 Git에서 제외되는 `test-results/guest-stability-20261104/`에 보관한다.

최종 로컬 결과: 전체 단위 검사 477개 통과, 실제 Redis 설정이 필요한 선택 검사 2개 제외, 실패 0개다. 새 입력 복구 회귀 검사는 12개 모두 통과했다. 아래 브라우저 검사 4종과 204개 외부 JavaScript 파일 구문 검사도 통과했다.

- 새 순수 로직 회귀 검사: 순서 변경, 연속 유실과 중복 도착, 방향 전환, 120Hz 세부 프레임, 라운드·몸체·연결 변경, 미완성 입력 초기화, 이전 형식과 전환, 잘못된 입력, 이동 시간 예산을 검사한다.
- 브라우저 `browser-net-lag.js`: 지연, 순서 변경, 송신 버퍼 밀림, 핑, 입력과 스냅샷 경로를 검사한다.
- 브라우저 `browser-net-wave2.js 2`: 입력 확정과 위치 보정, 방장이 움직이는 몸체, 100ms 편도 지연에서 이동 후 정지를 검사한다.
- `browser-network-recovery.js`: 모의 전송에서 상태 채널 대체, 로비·대전 재접속과 기존 몸체 복구를 검사한다.
- `browser-online.js`: 로컬 PeerServer와 실제 WebRTC 데이터 채널의 연결·교체를 검사한다.

브라우저 측정 도구 `net-lag-harness.js`는 렌더링을 끈 두 페이지 사이의 전송·위치 처리를 측정한다. 서로 다른 실제 인터넷 회선, 휴대폰 하드웨어, 실제 사용자의 전체 대전이나 프레임 개선율을 검증하는 도구는 아니다. Android·실결제 검사는 실행하지 않는다.

같은 도구의 6초 측정에서 위치 보정이 발생한 스냅샷 수는 다음과 같다. 브라우저 스케줄링과 장면 충돌의 영향을 받는 표본이며, 실서비스 개선율을 뜻하지 않는다.

| 전송 조건 | 수정 전 | 최종 수정 후 |
| --- | --- | --- |
| 25ms 편도 지연, ±3ms 변동 | 39 / 120 | 17 / 120 |
| 40ms 편도 지연, ±25ms 변동 | 119 / 119 | 19 / 120 |
| 40ms 편도 지연, 변동·재전송·순서 변경 | 102 / 102 | 23 / 104 |

실제 환경에서 남은 멈춤이 발생하면 당시 FPS, 핑, 마지막 스냅샷 간격, 입력 송신 지연과 ICE 연결 경로를 함께 수집해야 한다. Cloudflare Workers 요금제 변경이나 신호 서버의 호스팅 이전만으로 이 문제가 해결된다고 판단할 근거는 없다.
